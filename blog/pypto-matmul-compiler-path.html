MatMul in PyPTO, the compiler path

Ascend's AI Core is not a SIMT (Single Instruction, Multiple Threads) device with a compiler-managed cache in front of it — it's two independent cores, a cube and a vector unit, each running its own program (MPMD: Multiple Program Multiple Data) and reaching each other only through global memory. A DSL built for that model can't hide memory placement behind an implicit-cache abstraction the way a GPU-shaped one can. 05_matmul.py makes that explicit: six lines, five memory spaces named, one line per hop. This page traces the same kernel through the compiler — tile IR, an automatic-tiling pass with a real cost model, generated Ascend C, the toolchain, the silicon — and back to the question a DSL-compiler researcher cares about: what has to be explicit here, what gets automated, and why.

Of 55 passes, 11 change the IR for the whole-tensor kernel and 8 for the hand-staged one — the same counts as before, but a different pass supplies the whole-tensor side of it now: AutoTileMatmulL0 does the tiling (its 128×256 shape is chosen specifically so it has real work to do), and InferTileMemorySpace — which used to be the one placing Left/ Right — is the no-op instead. The on-chip memory allocator's own contribution still reduces to setting a single integer, and the hand-staged kernel's six instructions still have no overlap at all — each waits on the one before it. Provenance. The hand-staged kernel's structure is observed, nothing measured, compiled for a2a3sim on backend Ascend910B — not timing-accurate, so no figure on this page states a cycle count, a bandwidth or a speedup. The whole-tensor kernel's structure is documented and test-fixture-verified, not independently dumped for this exact shape — see “Eleven passes out of fifty-five” for citations.

How this was made

I work on this compiler stack and had a pile of real pass dumps, PTOAS docs, and test fixtures already sitting in an internal notes repo. The observed / documented / reconstructed tiering you'll see throughout is the result of that back-and-forth, not a stylistic flourish.

The kernel under study

What you are looking at

@pl.jit
def matmul_64(a: pl.Tensor, b: pl.Tensor, c: pl.Out[pl.Tensor]):
    with pl.at(level=pl.Level.CORE_GROUP):
        tile_a_l1  = pl.load(a, [0, 0], [64, 64], target_memory=pl.MemorySpace.Mat)
        tile_b_l1  = pl.load(b, [0, 0], [64, 64], target_memory=pl.MemorySpace.Mat)
        tile_a_l0a = pl.move(tile_a_l1, target_memory=pl.MemorySpace.Left)
        tile_b_l0b = pl.move(tile_b_l1, target_memory=pl.MemorySpace.Right)
        tile_c_l0c = pl.matmul(tile_a_l0a, tile_b_l0b)
        pl.store(tile_c_l0c, [0, 0], c)
    return c

Every one of those six lines exists to demonstrate a different rung of the on-chip memory hierarchy. None of them is boilerplate, and none of them is optional — the move calls in particular are not stylistic hints the compiler could route around.

The reason this file feels verbose compared to 01_hello_world.py is that the cube unit does not read from the vector buffer. It has dedicated physical operand ports, and getting data into them is a two-hop journey that you are being made to write out by hand, once, so that you understand what the compiler does for you later.

Read this file as the fully-manual endpoint of a spectrum, not a standalone example. Later on this page (§ The same matmul, four ways) the exact same computation gets compiled from a whole-tensor pl.matmul call with no memory spaces named at all — the compiler derives everything this file writes out by hand. PyPTO has no separate schedule language to express that automation in, the way Halide or TVM do; the automation is a pass over this same program. The six lines below are best read as a manually unrolled schedule, not boilerplate.

An overview before the detail sections

Six lines of Python, six instructions on silicon

Each section below expands one stage of this pipeline. Step through it once here first — the same six colors reappear as a small badge on every section that covers one stage in depth.

Why this pipeline has this shape

A GPU kernel compiler can treat memory placement as an optimization detail because every SM runs the same program (SIMT) against a hardware cache the compiler is free to manage implicitly. Ascend's AI Core is MPMD (Multiple Program Multiple Data): the cube core and the vector core run independent programs, each with its own Scalar Unit, exchanging data only through global memory. There is no shared cache for a compiler to manage on your behalf across that boundary — so the placement decisions stage 1 below writes out by hand are not stylistic; they are the DSL surfacing a real hardware fact a SIMT-shaped language like Triton or CUDA C++ never has to.

Why the move calls are not optional

Left and Right are physical ports

The single most common misreading of this example is that Left and Right are a naming convention for "first argument" and "second argument". They are not. They are two separate physical buffers — L0A and L0B — wired to two different operand feeds of the MAC array. The operator registration says so directly: 

// REGISTER_OP("tile.matmul") in src/ir/op/tile_ops/matmul.cpp (registration preamble omitted)
REGISTER_OP("tile.matmul")
    // .set_op_category(...), .functional_execution_memory_access(), .set_description(...),
    // .add_argument("lhs", ...), .add_argument("rhs", ...) elided above
    .set_input_memory(0, Left)      // arg 0 MUST be in L0A
    .set_input_memory(1, Right)     // arg 1 MUST be in L0B
    .set_output_memory(Acc);        // result is always L0C

Two consequences a new user should internalise straight away. First, swapping the two move targets does not compute a transpose — it is rejected by the operand memory constraints. Second, you never write MemorySpace.Acc anywhere in this kernel, because the op's own registration puts the result there.

The accumulating sibling follows the same shape: tile.matmul_acc is registered as (Acc, Left, Right) → Acc, in-place on argument 0. That is exactly why intermediate/04_matmul_acc.py can write acc = pl.matmul_acc(acc, …) and have the second K-chunk land on top of the first without a copy.

The memory-space argument on target_memory= functions as a type, not a hint. The op's set_input_memory/set_output_memory declarations are a static, per-argument constraint the type deducer enforces at compile time — the DSL rejects an illegal placement the same way a type checker rejects an ill-typed program, before any code runs. That is the mechanism behind "rejected, not silently transposed" above: the placement is checked statically, at the same point argument types are.

Reference table

Six spaces, and who can reach them

The mental model that matters: these are separate buffers, not a nesting. L0A is not "inside" L1 the way L1 is inside a CPU's cache hierarchy. Each is its own SRAM with its own capacity and its own legal predecessors. This is the table a Triton or TileLang kernel never needs — those DSLs manage an implicit cache the compiler owns; PyPTO's memory model is these nine explicit spaces, named in the type, with an explicit pl.load/pl.move/pl.store at every hop between them. The capacities are the 910B figures the backend actually compiles against; on A5 the accumulator doubles to 256 KiB and the bias buffer to 4 KiB, which is the kind of difference that silently changes which tilings are legal.

The load rule

A DDR-facing pl.load may target only Vec or Mat. It defaults to Vec, which is why examples 01–04 omit the argument entirely. There is no way to load straight into Left — the two-hop path is the hardware's, not the DSL's.

The store rule

pl.store has no target_memory parameter at all — the destination is always DDR. It accepts Vec or Acc as its source, which is precisely what makes the direct L0C → GM store on the last line legal.

pl.matmul is a type-dispatched wrapper with two very different personalities depending on whether you hand it Tiles or Tensors.

Type deduction also enforces that the physical K matches exactly, that rhs's valid K covers lhs's, and that both operand dtypes are identical. The result memory space is always Acc.

Numerics

This is why the example asserts with rtol=1e-3, atol=1e-3 while 04_activation.py uses 1e-5. The cube accumulates in FP32 and writes back through FIXPIPE; the result is not bit-identical to torch.matmul. If you copy a 1e-5 tolerance from a vector example onto a cube kernel, it will fail and you will go looking for a bug that isn't there.

Why this matters later

A reader who takes "64×64" as the cube's native tile size will be confused the moment they open advanced/02_auto_tile_matmul.py and find the compiler choosing k = 64 with independent m/n sub-tiles, or discover that INT32 has a 32-row L0C alignment on 910B. Anchor on 16 and those all follow.

This is a real search problem, not a lookup table

When AutoTileMatmulL0 (pass 19, see the compiler ladder below) picks tile shapes for you, it isn't consulting a table of good sizes for common cases — it runs an exhaustive roofline search over the design space P = (m, n, k, stationarity, dbC): every legal 16-aligned (m, n, k), crossed with which operand stays stationary in L0 (output-stationary keeps Acc resident and streams A/B chunks through it — the K-loop below is exactly this; A- or B-stationary instead pin one operand in L0A/L0B and stream the output and the other operand — this derives the other two's double-buffer depths, not searched independently), crossed with the accumulator's double-buffer depth. The cost model estimates wall-clock core cycles per candidate — including the pipeline fill/drain bubble a naive "hide the drain behind compute" model would miss on small grids — and returns the minimum. It is model-driven, not behavior-neutral: the chooser's optimum is checked against a brute-force re-enumeration of the same cost model, not against real hardware, so it is a solver-correctness guarantee, not a performance one. The tilings it picks do run on real Ascend910B hardware and get checked there — tests/st/runtime/ops/test_auto_tile_matmul.py is on-device, torch-golden validation — but that's checking the chosen tiling produces the right numbers, not that it's the fastest legal one. Nothing in the pass's own test suite, or on this page, measures the picked tile size against a timed alternative.

What the chooser actually emits, once it has to split

The slider above answers a residency question: does the shape fit in one L0 tile. When it doesn't, AutoTileMatmulL0 doesn't fail or fall back to a slower path — it rewrites the single tile.matmul call into a loop, or a grid of loops, over L0-sized sub-tiles. These are the pass's own two canonical examples, from its documentation (docs/en/dev/passes/18-auto_tile_matmul_l0.md), reproduced here rather than reconstructed for this page.

Output fits L0c, K doesn't — one K-loop

M = N = 128, K = 256. The chooser picks (m, n, k) = (128, 128, 64) — the output stays whole; only the reduction is tiled. 

# before
c: pl.Tile[[128, 128], pl.FP32] = pl.tile.matmul(a_mat, b_mat)
# after
c_l0_init = pl.tile.create([128, 128], pl.FP32, target_memory=Acc)
for ko, (c_iter,) in pl.pipeline(0, 256, 64, init_values=(c_l0_init,), stage=2):  # this 2 is dbC from the search space above
    sa = pl.tile.extract(a_mat, 0, ko, [128, 64], target_memory=Left)
    sb = pl.tile.extract(b_mat, ko, 0, [64, 128], target_memory=Right)
    c_acc = pl.tile.matmul_acc(c_iter, sa, sb, ko == 0)
    c = pl.yield_(c_acc)
# c (the yield-LHS) holds the accumulated Acc-typed result.

One buffer, not two: tile.matmul_acc writes back into its own accumulator operand (set_output_reuses_input(0)), so the loop-carried c_iter/c_acc is one L0C tile for the whole reduction. The ko == 0 predicate is what makes the first iteration overwrite instead of accumulate — there is no separate zero-init step.

What stage=2 actually buys: two iterations, not four

The dependence diagram earlier on this page shows a kernel with no overlap at all, and says why: double buffering and K-splitting exist to give overlapping pipe stages a second tile to work on, and a single-tile kernel has nothing to overlap. This loop is that second tile. Two of its four iterations, shown on the same four pipe lanes:

Output exceeds L0c — a grid of K-loops

M = N = K = 512, FP32. A whole [512, 512] FP32 accumulator is 1 MiB — nowhere close to a 128 KiB L0C. The chooser picks (m, n, k) = (256, 256, 32): a 2×2 grid of output sub-tiles, each running its own pipelined K-loop. 

# before
c: pl.Tile[[512, 512], pl.FP32, pl.Mem.Acc] = pl.tile.matmul(lhs_mat, rhs_mat)
out = pl.store(c, [0, 0], out)
# after — one of four sub-tiles shown; the other three are the same shape,
# at (mi=0,ni=0), (mi=0,ni=256) and (mi=256,ni=256)
# Sub-tile (mi=256, ni=0): rows [256:512], cols [0:256].
c_t1_init = pl.tile.create([256, 256], dtype=pl.FP32, target_memory=Acc)
for ko, (c_iter,) in pl.pipeline(0, 512, 32, init_values=(c_t1_init,), stage=2):
    sa = pl.tile.extract(lhs_mat, 256, ko, [256, 32], target_memory=Left)
    sb = pl.tile.extract(rhs_mat, ko, 0, [32, 256], target_memory=Right)
    c_t1_acc = pl.tile.matmul_acc(c_iter, sa, sb, ko == 0)
    c_t1 = pl.yield_(c_t1_acc)
out_t1 = pl.store(c_t1, [256, 0], out_t0)  # store sub-tile to out[256:512, 0:256]

All four sub-tiles are independent 2-stage-pipelined K-loops, same shape as the single-loop case above, just four of them. The output tensor threads through them in SSA form (out → out_t0 → out_t1 → out_t2 → out_t3), and the full, oversized [512, 512] accumulator is never materialized anywhere — only one [256, 256] Acc tile exists on-chip at a time, per sub-tile.

Tiles don't have to divide the shape evenly

A 256×256 FP32 matmul on this backend picks (m, n) = (192, 160) — neither divides 256. The pass tiles into four boundary sub-tiles of logical shape 192×160, 192×96, 64×160 and 64×96, peeling the remainder rather than requiring the grid to divide the output evenly. Splitting the output adds FIXPIPE drains, one per sub-tile; splitting K does not, since partial sums accumulate in one L0C and drain once per output block — which is why the chooser tiles M/N only when the output itself doesn't fit, never as a substitute for K-tiling.

PASS 0 / 11

This is the pass now — it wasn't before

AutoTileMatmulL0 runs at 19 and, at this page's original 128×128 FP16 shape, used to leave the IR byte-identical: the operands occupied 32 KiB of a 64 KiB L0A and L0B, so there was no subdivision to make. Push the sliders in “when does a shape stop fitting L0” past those capacities and this is exactly what changes. At K=256, a whole-K FP32 L0A slab would be 128×256×4 = 131072 bytes against a 64 KiB capacity — over by 2× — so the pass tiles K into four 128×128×64 blocks, each slab 128×64×4 = 32768 bytes, exactly half of L0A, leaving room to double-buffer the pipelined K-loop. Grounded in the pass's own worked example at docs/en/dev/passes/18-auto_tile_matmul_l0.md:151–181.

So which pass writes Left and Right now?

Still not InferTileMemorySpace, at 21 — that's the twist. Once AutoTileMatmulL0 tiles a matmul, its own per-iteration tile.extract(..., target_memory=Left) calls place the operands directly; by the time pass 21 runs two passes later, there's nothing left unplaced. This is the page's new no-op — the same role AutoTileMatmulL0 played two paragraphs ago, traded to the pass that used to do the placing. The hand-staged kernel still needs InferTileMemorySpace for its own two move calls — only the whole-tensor kernel's compiler-driven path skips it, because AutoTileMatmulL0 already did that job on the way past.

And why the reuse pass had nothing to do — for two different reasons

MemoryReuse — which runs immediately before allocation — leaves the IR byte-identical for both kernels, but not for the same reason. advanced/02

auto_tile_matmul — the payoff

Whole-tensor pl.matmul, no memory spaces at all. Which pass fills that in depends on the shape, and it is worth being precise, because the obvious answer is backwards once tiling activates: ConvertTensorToTileOps (12) stages both operands into Mat, and AutoTileMatmulL0 (19) enters once the shape stops fitting L0 — at which point it owns M/N tiling and full-K versus split-K, and places Left/Right directly on its own per-iteration tile.extract calls. InferTileMemorySpace (21), which inserts the Left/Right moves when a shape already fits L0 whole, has nothing left to place once AutoTileMatmulL0 already has — for the 128×256 case compiled for this page, that's exactly what happens; see “Eleven passes out of fifty-five” for what AutoTileMatmulL0 actually emits. The pass has since grown into six kernels spanning a real design matrix: placement (DDR vs Mat/fits-L0C) × K-strategy (split vs full) — ddr_split_k, ddr_full_k, mat_split_k, mat_full_k, fits_l0c_full_k, fits_l0c_split_k. It also demonstrates a cast-fold: an rint narrowing cast fused directly into tile.assemble, so FIXPIPE does the rounding on the way out instead of a separate vector pass.

Where's the schedule?

There isn't a second one. Halide separates algorithm from schedule as two artifacts you author; PyPTO doesn't expose an equivalent schedule IR at all — tiling is a property-gated pass over the same program, and the pass is built to detect how much you already specified rather than assume it owns every decision. AutoTileMatmulL0's own contract states it plainly: "an operand already placed in Left or Right is a manual L0 scheduling decision, so AutoTile does not silently replace or subdivide it." beginner/05 above and this whole-tensor call are the same pass's two endpoints, not two different compilers.

The pass's position in the pipeline is not incidental either. It runs at pass 19, immediately after LegalizeTileCast (18) and before CanonicalizeTileSlice (20) and InferTileMemorySpace (21) — a point where every tile op is already 2D but no memory space has been inferred yet. That ordering is why AutoTileMatmulL0 has to emit its own explicit target_memory=Left/Right/Acc kwargs rather than leaning on inference that hasn't run: InferTileMemorySpace two passes later reconciles and backfills whatever this pass didn't stamp. PyPTO's pass manager enforces this kind of ordering structurally — every pass declares the IR properties it requires, produces, and invalidates, and the pipeline rejects an ordering violation at construction time, not by re-running a stale analysis the way LLVM's legacy pass manager or MLIR's AnalysisManager would. AutoTileMatmulL0 requiring "tile ops are 2D" and explicitly not requiring "memory spaces are known" is that property contract, made concrete.

advanced/01

Not about memory spaces but about cores: pl.parallel over K with pl.assemble(…, atomic=pl.AtomicType.Add). Note the accumulation order across cores is not fixed, so results are non-deterministic at the ulp level.

The two ends of the ladder, compiled

Same computation, same compiler, three passes apart

The top and bottom rungs are not two compilers or two schedules — they are the same pipeline reaching the same place from different starting points. Compiling both with per-pass dumps makes the claim measurable: which passes had to do something, and which had nothing left to do because the source already said it.

Same point, restated concretely

There is no schedule object anywhere in that list. The manual kernel does not disable a pass or select a policy; it simply arrives at pass 12 with nothing left for pass 12 to do. That is what “the automation is a pass over the same program” means operationally — and it is why beginner/05 and a bare pl.matmul can be two ends of one spectrum rather than two languages.

Stage 3 · PTOAS

Between the .pto module above and the C++ kernel below

PTOAS's own pipeline

Back to the hand-staged 64×64 kernel — the one with a real compile behind it, not the reconstructed whole-tensor comparison. Everything above this section happened inside PyPTO. What follows happens inside a second, independent compiler: PTOAS, an out-of-tree LLVM/MLIR tool that parses the .pto module PyPTO wrote, runs its own pass pipeline over it, and lowers the result to the C++ shown next. That pipeline is real and documented (tools/ptoas/ptoas_pipeline.cpp), and it is not the same list of passes as PyPTO's Tile IR pipeline above — it is solving a different problem, one level lower.

Two things I had backwards, and how I found out

The table above describes eleven passes in the abstract; two of them — pto-insert-sync here, and emit-pto-manual further down — have an effect on this kernel that can be shown as real IR rather than description. Getting there meant correcting two assumptions an earlier version of this section made, both in the same direction: crediting a pass with deciding something PyPTO itself had already decided.

Sync. This section used to credit pto-lowering-sync-to-pipe with producing the four flag pairs below, on the assumption that PyPTO's codegen places record_event/wait_event hints for something downstream to lower. A real .pto dump for this exact kernel (presentations/diagrams/slideshow/matmul_codegen_example/ptoas/matmul_64_incore_0.pto) shows the opposite: PyPTO emits zero sync ops. pto-lowering-sync-to-pipe has nothing to lower; pto-insert-sync — confirmed unconditional by reading PyPTO's own _get_ptoas_flags() (pto_backend.py:1332–1358), not opt-in the way the bare ptoas CLI's own default suggests — solves the whole dependency graph from a blank slate, every compile.

Layout. Same shape of mistake. PTOAS.md documents pto-infer-layout as inferring an nd/dn/nz hint onto make_tensor_view ops with static shape and stride, and this section used to take that at face value rather than show the literal syntax. Checking PyPTO's own codegen instead: pto_codegen.cpp:1526 stamps this attribute on every make_tensor_view PyPTO ever writes, unconditionally — the real line, already present before PTOAS runs at all: 

%a__ssa_v0_view = pto.make_tensor_view %arg0, shape = [%c64_index, %c64_index],
    strides = [%c64_index, %c1_index] {layout = #pto.layout<nd>} : !pto.tensor_view<?x?xf32>

pto-infer-layout is a real pass with real work to do, just not on PyPTO-generated .pto, which never arrives without this attribute set. It's also solving a different problem than the layout seen earlier in the pipeline overview (blayout=col_major/slayout=row_major): that comes from PyPTO's own ResolveBackendOpLayouts (Tile IR pass 23) and describes the cube operand's row/column layout, not the DMA-facing nd/dn/nz hint above — a different property, on a different kind of value, that PyPTO also happens to answer before PTOAS ever sees the file. It's not a cosmetic hint either: PTOAS.md §12.2 says the codegen pass reads it to pick the DMA intrinsic variant — nd for a row-major transfer, dn for column-major, nz for fractal/blocked. Get it wrong and the DMA strides through memory the wrong way; the tile arrives with the right bytes in the wrong order, not a slower correct one.

One more sync point this page hadn't mentioned

The real emitted kernel ends with a call this page never showed: ptoas_auto_sync_tail(PTOAutoSyncTailMode::kBarrierAll), which expands to a full pipe_barrier(PIPE_ALL) right before the function returns. It sits outside the #if defined(__DAV_CUBE__) guard shown further down — unconditional, common code, not part of the cube-specific instruction sequence. It isn't one of the four data-dependency flag pairs above and isn't gated by anything pto-insert-sync computed from the dependency graph; it runs on every kernel as an exit-boundary safety net, not a data hazard. The “six instructions, no overlap” claim at the top of this page is still accurate for the six data-carrying instructions — there is just a seventh, unconditional one guarding the function's exit that this page hadn't accounted for until now.

The codegen phase — more than one pass

pto-insert-sync hands off to a chain of six real steps, not one:

  1. emit-pto-manual converts every PTO op into an emitc.call — MLIR's EmitC dialect (a different sub-language sharing the same IR infrastructure as PTO, the dialect this whole page has been reading up to this point) — still IR, not text.
  2. emitc-form-expressions cleans that up.
  3. A second cse cleans it up further.
  4. Two MLIR-level fixups run: dropEmptyEmitCExpressions and materializeControlFlowOperands.
  5. translateToCpp — the actual MLIR→text step, never itself listed as a “pass” — prints it as C++.
  6. A final string-level rewrite turns any PTOAS__* marker call into real member-function syntax (PTOAS.md §12.3).

This kernel doesn't exercise that last step — every op below is a plain function call, not a .SetValue()/.data()-style member call — so it's a no-op here, same as the function-reordering step after it (one function, nothing to reorder). It isn't optional in general, though: native EmitC can't express C++ member-function calls at all, so PTOAS's own codegen would be stuck without this string-level patch for any kernel that does have one. The diff below is still accurate end to end, PTO MLIR in and C++ out — it's just six steps doing it, not one, and the EmitC-dialect IR in between isn't shown, for the same reason pto-infer-layout's attribute syntax isn't shown further down: PTOAS.md confirms the op family (emitc.call) but not this kernel's literal argument syntax.

Stage 4 · The emitted kernel

The floorplan above, on real silicon

PyPTO's matmul compiler path

This is what comes out the far end of the pipeline just described, for the hand-staged 64×64 kernel — specifically emit-pto-manual, the pass that does the actual PTO→C++ conversion. Same eight moments as the walkthrough above — Mat is really the L1 Buffer, Left/Right are really L0A/L0B, Acc is really L0C. And the code beside it is no longer an illustration: it is what this kernel compiles to. Six lines of Python, six instructions. The __DAV_CUBE__ guard is the MPMD split from the top of this page made literal — one generated file holding two independent programs, partitioned by a preprocessor macro.

Ready. Nothing on-chip yet. This is the same real AIC (cube core) and AIV (vector core) layout every PyPTO cube kernel targets — step through to see matmul_64 walk it.

Tier: observed — tile handles renamed for width, nothing else changed. Identical in both compiles: the hand-staged 64×64 kernel emits the same six instructions and the same four events.

The four events those six instructions hang on

The instructions are not the whole story; the set_flag/wait_flag pairs between them are. Each one names a producer pipe and a consumer pipe, and together they are the dependence graph the hardware is actually given. Drawn out, the graph says something the listing does not.

Read the arrows: there is no overlap

Every event edge runs from one instruction to the instruction immediately after it. There is no point at which two pipes are both busy: MTE2 finishes before MTE1 starts, MTE1 before the cube, the cube before FIXPIPE. Four functional units, and at any moment three of them are idle. This is expected for a kernel with exactly one tile of each operand: double buffering, K-splitting and the L0 tiling search all exist to give overlapping pipe stages a second tile to work on, and a single-tile program gives them nothing to overlap. The compile-time hint this kernel raises reflects the same limitation from the memory side: PH001 flags the 256-byte innermost row against a 512-byte L2 line, and the same fix — a wider tile — addresses both the idle lanes and the hint.

Stage 7 · Execute

Two details that are not about matmul

The wrapper and the out-parameter

pl.at(level=pl.Level.CORE_GROUP)

This wraps the body in every beginner example, not just this one. It is the scope that gets outlined into a device kernel. CORE_GROUP is value 2 — "1 AIC + 2 AIV", the InCore kernel level. At that level with no optimizations, pl.at produces a ScopeStmt(InCore); every other level produces a Hierarchy scope.

Level#Meaning
AIV0Single vector core
AIC1Single cube core
CORE_GROUP21 AIC + 2 AIV
CHIP_DIE3Chip die
CHIP4Chip / UMA
HOST5Single OS instance
CLUSTER_0…26–8Pod, supernode, cross-rack
GLOBAL9Global coordinator

Which physical unit actually runs this? AIC and AIV above name real hardware roles, not just DSL levels — AIC = AICore-CUBE, the matrix unit this whole page has been drawing; AIV = AICore-VECTOR, the elementwise unit matmul_64 never touches; the AICPU is the scheduler that dispatches to whichever one a kernel targets, never a compute worker itself. AIC and AIV are exactly the two independent programs the MPMD framing at the top of this page refers to — this table is PyPTO's DSL-level view of that same split.

c: pl.Out[pl.Tensor] and return c

c is both an output parameter and a return value, which looks redundant until you see it called from an orchestration function.

The in-place mutation through the Out parameter is what actually delivers the result. The return c exists for composability — it is what lets intermediate/01 write: 

mm_out = pl.create_tensor([64, 64], dtype=pl.FP32)
mm_out = _matmul_kernel_64x64(a, b, mm_out)
c      = _add_bias_kernel_64x64(mm_out, bias, c)

Each call threads the buffer through to the next, so the orchestration reads as dataflow rather than as a sequence of mutations.

Before you go

What you've actually seen

Two kernels, the same journey, different endpoints. The hand-staged 64×64 kernel is real all the way down: a real compile, a real .pto module, a real PTOAS pass pipeline that mostly declines to act, and six real instructions with no overlap, checked byte-for-byte against the actual compiled artifacts. The whole-tensor 128×256 kernel is reconstructed from AutoTileMatmulL0's own documented worked example, not an independent compile — and it never stops at six instructions, because it tiles: a pipelined K-loop, double-buffered, with real overlap across iterations shown earlier in this page. Different tiers of evidence, tiered honestly throughout; the same DSL → Tile IR passes → PTOAS's own pipeline → hardware trip, walked twice, once for each answer to “what happens when the shape doesn't fit in one tile.”

Nothing on this page is privileged information

Do this yourself

Every figure above came out of two compiles and two command-line tools that ship in the tree — with one exception: the “PTOAS's own pipeline” table is read off PTOAS's documented pass contracts, not an independently re-dumped PTOAS-side trace (its own tier note says so). Everything else is one environment variable, one RunConfig flag, and a diff. Before reasoning about what a compiler did, ask it to show you: the steps below reproduce every other figure on this page.

Ask for the dumps

PassDumpLevel.EXPLICIT writes one IR snapshot per pass. That is the only thing separating a normal compile from everything on this page. 

import os
os.environ["PYPTO_PROG_BUILD_DIR"] = OUT   # read per process — set it before you compile

import torch
import pypto.language as pl
from pypto.ir.pass_manager import PassDumpLevel
from pypto.runtime import RunConfig

@pl.jit
def matmul_tiled(a: pl.Tensor[[128, 256], pl.FP32],
               b: pl.Tensor[[256, 128], pl.FP32],
               c: pl.Out[pl.Tensor[[128, 128], pl.FP32]]):
    with pl.at(level=pl.Level.CORE_GROUP, name_hint="matmul"):
        c[:] = pl.matmul(a, b, out_dtype=pl.FP32)
    return c

cfg      = RunConfig(dump_passes=PassDumpLevel.EXPLICIT)
compiled = matmul_tiled.compile(a, b, c, config=cfg)
print(compiled.output_dir, compiled.platform)

matmul_tiled(a, b, c, config=RunConfig())   # then run it and check the numbers

Three things that are easy to get wrong

  • PYPTO_PROG_BUILD_DIR is read once per process. Set it before the first compile or your artifacts land somewhere else.
  • Without dump_passes there are no snapshots at all — not a quieter set, none.
  • name_hint is what gives the outlined InCore function a readable name in every later dump. Skip it and the function filter has nothing to filter on.

Swap the body for beginner/05_matmul.py's six lines and you have the other compile this page compares against, with no other change.

Find the passes that matter

55 snapshots is too many to read and the wrong number to reason about. The useful set is the ones that changed something, and finding them needs nothing installed: 

prev=""; for f in $(ls passes_dump/*.py | sort -V); do
  [ -n "$prev" ] && ! diff -q "$prev" "$f" >/dev/null && echo "CHANGED $(basename $f)"
  prev="$f"
done

The in-tree viewer does the same and adds per-pass line counts, character-level diffs, function filtering and any warnings a pass logged:

python -m pypto.tools.ir_trace passes_dump/ -o ir_trace.html

The method, which is the transferable part

Filter to the passes that changed the IR, then filter by function. On this kernel that is 55 down to 11, and those 11 are the entire stepper further up this page. The same two filters work on any kernel you compile; the equivalent views also exist as an editor extension if you would rather click than diff.

Draw the memory map

python -m pypto.tools.memory_map passes_dump/38_after_AllocateMemoryAddr.py -o map.html

Address across, lifetime down, one rectangle per MemRef — and a high-water mark per space against that backend's capacity, so you can see at a glance how much of L0 a tiling decision is actually spending. It reads the dump as Python rather than by pattern-matching text, and takes the lifetime axis from the statement order in the file itself.

Read the hints you were already given

The hand-staged compile on this page is numerically correct and still raises a complaint. It is sitting in report/perf_hints.log the whole time: 

[perf_hint PH001] TileInnermostDimGranularity: tile.load has innermost dim = 256B
(tile fp16[128], target_memory=Mat); moves 32768B as 128 x 256B rows;
recommended >= 512B for backend a2a3 (L2 cache line = 512B).
Consider increasing tile shape on the innermost axis.

Decoded: each row of the staged tile is 128 FP16 values, so 256 bytes, so every row transfer uses half of a 512-byte L2 line. The tile is correct, fits, and passes its tolerance check — and still moves its data at half the granularity the backend wants. Correctness and efficiency are checked separately here, and the hint log is where the second check's results end up.

Push the same shape further and watch the compiler change its mind again

This page's own whole-tensor kernel already shows one flip: it was grown from 128×128 to 128×256 specifically so AutoTileMatmulL0 would have real K-tiling work to do (see “Eleven passes out of fifty-five”). Push M or N up too — past L0C capacity, not just L0A/L0B — and the pass changes its mind a second time: 

a: pl.Tensor[[512, 512], pl.FP32]    # 512x512 FP32 -> C needs 1 MiB of a 128 KiB L0C

19_after_AutoTileMatmulL0.py stops K-only tiling and starts M/N-tiling the output into a grid too, stamping a sub-tile structure onto the IR instead of a single K-loop — the M/N-tiling example in “64 is not the cube's granularity” shows exactly this shape's real before/after, from the pass's own documentation. This is the same relationship argued above, observed from the opposite direction: the pass does exactly as much work as the source leaves for it.

Where the runtime views start

Everything above is static: it describes what the compiler produced, never what the hardware did with it. Core timelines, task-dependency graphs and per-function timings come from runtime records instead, which the framework writes under dfx_outputs/: 

RunConfig(enable_chip_swimlane=4, enable_dep_gen=True)
# -> dfx_outputs/chip_swimlane_records.json  — AICore / AICPU / orchestrator timeline
# -> dfx_outputs/deps.json                   — task DAG, tensors, redundant edges
# -> dfx_outputs/name_map_<ts>.json          — Func ID to function name

Those need a real device. The compiles behind this page target a2a3sim, which is not timing-accurate, which is why no figure here carries a duration and why the dependence diagram above is careful to label its horizontal axis as issue order. The structure is observed; the speed is not.
